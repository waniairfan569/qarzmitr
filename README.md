# QarzMitr — قرض متر

**Turning a shopkeeper's paper ledger into a verifiable credit score.**

Built for the Alibaba Cloud AI Hackathon Pakistan 2026 — Financial Inclusion track.

---

## The problem

Between 161 and 182 million Pakistanis are unbanked. A shopkeeper with a decade of steady trade has no credit history a microfinance institution can act on, because none of it was ever recorded in a form a lender recognises.

But it *was* recorded. Every sale, expense, and customer debt sits in a handwritten paper ledger — a *khata* — written daily in a mix of Urdu and English.

QarzMitr reads that ledger from a photograph and turns it into a credit score, with **zero behaviour change required** from the shopkeeper. No app to adopt, no bank account to open. It works for someone who has never used a banking app and never will.

---

## How it works

```
photo of a khata page
        ↓  POST /upload          Qwen-VL-Plus reads the handwriting
raw Urdu/English text
        ↓  POST /structure       Qwen-Plus types each line
sale · expense · credit_given · repayment
        ↓  POST /score           deterministic backend maths
score 0–100  +  Urdu explanation
        ↓  GET /dashboard
shopkeeper view  ·  lender view
```

### The score is not generated by AI

This is the central design decision. Three metrics are computed **in ordinary backend code**, combined at fixed weights, and saved as a new row so history is preserved:

| Metric | Weight | How it's measured |
|---|---|---|
| Cash flow consistency | 40% | `100 / (1 + CV)` where CV is the coefficient of variation of weekly net income |
| Repayment ratio | 35% | `clamp(repaid / credit extended, 0, 1) × 100`, neutral 50 when no credit was ever extended |
| Revenue trend | 25% | Least-squares slope of daily sales, mapped against mean revenue |

Re-running the same ledger always produces the same score. A language model is used **only** to transcribe the handwriting and to explain the finished result in Urdu — it is never asked what the score should be.

Guards: fewer than 3 transactions, or sales on fewer than 2 distinct dates, returns `422` explaining what's missing rather than inventing a confident number.

## Verified end to end

A ledger page with ten mixed Urdu-English entries was pushed through the full chain against live Alibaba Cloud infrastructure:

- **12 of 12 lines** transcribed
- **10 of 10 transactions** correctly typed
- **71/100** scored, with a fluent Urdu explanation

### What happens when it misreads

The vision model made two genuine transcription errors, and both were caught rather than hidden:

| On the page | Read as | What the structuring step said |
|---|---|---|
| دہی (yoghurt) | دبی (Dubai) | `cash sale of milk and dubai (likely dairy product)` |
| آٹا (flour) | آئنا (non-word) | `expense for 10kg aina (likely flour or atta)` |

Both rows were still typed correctly. The uncertainty travels with the row into the database, where a reviewer can see exactly which entries to check. A system that reads handwriting *will* misread handwriting; the design question is whether it tells you.

## Running it

Requires Node 18+.

```bash
# Backend
cd backend
cp .env.example .env          # set JWT_SECRET at minimum
npm install
npm run db:init               # create tables
npm run seed                  # load a demo shopkeeper
npm start                     # http://localhost:3000

# Frontend, in a second terminal
cd frontend
cp .env.example .env
npm install
npm run dev                   # http://localhost:5173
```

### Configuration

Only `JWT_SECRET` is strictly required. Every integration below degrades safely when its credentials are absent — the feature reports itself unavailable instead of crashing.

| Variable | Enables | Without it |
|---|---|---|
| `DASHSCOPE_API_KEY` | OCR, structuring, Urdu explanation | Each step returns `skipped` with a stated reason |
| `DASHSCOPE_BASE_URL` | A workspace-scoped Model Studio gateway | Falls back to the public Alibaba endpoint |
| `OSS_*` (4 values) | Ledger images stored in Alibaba OSS | Stored on local disk |
| `GOOGLE_*` (3 values) | Google sign-in | Button hidden, endpoint returns 503 |
| `SMTP_*` | Emailed password reset links | Link written to the server log |

## Authentication

Three ways into one account record:

- **Password** — bcrypt at 12 rounds, with the 72-*byte* limit enforced correctly (37 Urdu characters already exceed it)
- **Google** — server-side OAuth; a Google login matching an existing email claims that account rather than duplicating it, and the original password keeps working
- **Reset link** — emailed, single-use, valid 30 minutes, stored SHA-256 hashed

Reset requests answer identically whether or not the address is registered, so the endpoint cannot be used to discover accounts. Each account carries a `token_version` that increments on reset and is checked on every authenticated request — so a password reset immediately evicts any session issued before it, rather than leaving a stolen JWT valid for days.

## Built with

**Frontend** React 19 · Vite 8 · Tailwind 4 · Recharts · React Router
**Backend** Node 18+ · Express 5 · better-sqlite3 · Nodemailer
**AI** Qwen-VL-Plus and Qwen-Plus via Alibaba Cloud Model Studio (OpenAI-compatible endpoint, `ap-southeast-1`)
**Storage** Alibaba Cloud OSS, with a local-disk fallback

Five tables — `users`, `ledgers`, `transactions`, `scores`, `password_reset_tokens`. Scores are written as new rows rather than updates, so the trend line is real history rather than a reconstruction.

---

## Status

This is a **feasibility prototype built to prove the pipeline is real**, not a finished lending product. No score it produces should decide a loan on its own, and the lender view's band thresholds are illustrative defaults rather than underwriting policy.

Known gaps, stated plainly:

- Google sign-in is implemented but not switched on — it needs OAuth client credentials
- The OSS storage path is correct but has not been exercised against a live bucket; local disk is the tested route
- Transcription accuracy has been measured on a small number of ledger pages, not at scale
